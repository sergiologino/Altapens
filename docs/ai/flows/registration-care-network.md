# Поток регистрации и привязки (семейная сеть заботы)

Документ фиксирует **действия пользователя** в типичных сценариях, чтобы проектировать понятный интерфейс и онбординг. Технические детали API не дублируются — только пользовательская логика «кто что делает».

---

## Роли

| Роль в интерфейсе | Кто это |
|-------------------|---------|
| **Родственник / опекун** | Взрослый, который настраивает заботу, видит сводки, приглашает близких. |
| **Подопечный** | Пожилой человек (или человек, за которым ухаживают): крупный экран, напоминания, SOS. |

Один человек в семье может быть только родственником или только подопечным в рамках одного профиля (два разных входа).

---

## Базовый принцип связи

1. **Код приглашения** создаёт тот, кто уже в приложении.
2. **Принимает** тот, кого приглашают: при регистрации вводит код (или переходит по ссылке с кодом).
3. После принятия в приложении появляется **связь заботы**: подопечный ↔ родственник (и при необходимости несколько человек с каждой стороны).

---

## Сценарий A: Первый опекун и первый подопечный (дедушка)

| Шаг | Кто | Действие |
|-----|-----|----------|
| 1 | Родственник | Открывает приложение → проходит **знакомство (онбординг)** → «Создать профиль» → роль **родственник или опекун** → регистрация (имя, почта, телефон, пароль). |
| 2 | Родственник | Попадает на **панель заботы**. Система может показать **короткую подсказку**: «Пригласите подопечного по коду». |
| 3 | Родственник | Раздел **«Приглашения»** → **«Создать код для подопечного»** → получает код (и при необходимости ссылку). Передаёт дедушке лично, по телефону или мессенджеру. |
| 4 | Подопечный (дедушка) | Открывает приложение → **«Создать профиль»** → роль **подопечный** → в поле **«Код приглашения»** вводит код → завершает регистрацию. |
| 5 | Система | Создаёт связь: дедушка видит **свой** крупный экран; родственник видит дедушку в списке **«Подопечные»**. |

**Точки путаницы (что прояснять в UI):**  
- Родственник не должен регистрировать дедушку «за него» без его участия — у подопечного свой аккаунт и свой вход.  
- Код вводит **тот, кого приглашают**, при своей регистрации (или отдельный экран «Принять приглашение»).

---

## Сценарий B: Тот же опекун добавляет второго подопечного (бабушку)

| Шаг | Кто | Действие |
|-----|-----|----------|
| 1 | Родственник | Уже вошёл в приложение. |
| 2 | Родственник | **«Приглашения»** → снова **«Создать код для подопечного»** → новый код (старый можно оставить активным или закрыть — по правилам продукта). |
| 3 | Подопечный (бабушка) | Как в шаге 4 сценария A: свой профиль, своя регистрация, **свой** код приглашения. |
| 4 | Система | В списке подопечных у родственника **два** человека; у каждого подопечного — своя связь с этим родственником. |

**Точки путаницы:**  
- Один код = одна новая привязка. На каждого нового подопечного — **новый** код.  
- В интерфейсе списка подопечных показывать **имена**, а не внутренние идентификаторы.

---

## Сценарий C: Второй опекун (например, второй ребёнок)

Идея: **подопечный** (или уже связанный родственник — по политике продукта) выдаёт приглашение человеку с ролью **родственник**.

| Шаг | Кто | Действие |
|-----|-----|----------|
| 1 | Подопечный или первый родственник | Создаёт приглашение **для родственника** (отдельный тип кода: «пригласить в заботу как опекуна»). |
| 2 | Второй родственник | **«Создать профиль»** → роль **родственник** → вводит **этот** код → регистрация. |
| 3 | Система | Второй опекун видит тех же подопечных, с которыми разрешена общая сеть (или только того, кто пригласил — по правилам доступа). |

**Точки путаницы:**  
- Код «для подопечного» и код «для родственника» — **разные сценарии**; в интерфейсе нужны **разные формулировки и кнопки**, чтобы не перепутать.  
- Подопечному не обязательно самому создавать код второму ребёнку — часто удобнее, если код создаёт **уже вошедший** родственник из настроек «Добавить опекуна» (если такой поток будет в продукте).

---

## Сценарий D: Подопечный заходит первым (реже)

| Шаг | Кто | Действие |
|-----|-----|----------|
| 1 | Подопечный | Регистрация **без** кода — возможен «пустой» профиль до привязки. |
| 2 | Родственник | Регистрация → создаёт код для подопечного. |
| 3 | Подопечный | **«Принять приглашение»** или ввод кода в профиле (если предусмотрено). |

*На MVP удобнее вести семью от **родственника**; этот сценарий описан для полноты.*

---

## Рекомендации для интерфейса

1. **Чек-лист после первого входа родственника:** например «1. Создайте код → 2. Отправьте близкому → 3. Дождитесь, пока он зарегистрируется».  
2. **Имена шагов в приглашениях:** «Код для пожилого человека» / «Код для ещё одного родственника» — без внутренних терминов.  
3. **История кодов:** кто создан, активен или принят — чтобы не дублировать лишний раз.  
4. **Онбординг (5–6 экранов)** — общие выгоды, безопасность, простота; отдельно кратко — «как связать семью» (см. экраны в приложении `/welcome`).

---

## Связь с онбордингом

Пользователь при первом открытии приложения видит слайды `/welcome`, затем попадает на `/start` (вход / регистрация). Это снижает тревожность до появления форм и объясняет **зачем** код и **две роли**.
